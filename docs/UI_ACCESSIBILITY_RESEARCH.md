# Accessible interfaces for the A-level simulation library

## Findings and design implications

- **Make the library easy to scan and navigate.** W3C identifies contrast sensitivity, fine motor control, and short-term memory as factors that can affect older adults’ web use. Its cognitive accessibility guidance recommends familiar controls, consistent placement, and clear headings. On the library and topic pages, pair course codes with course names, use descriptive simulation titles, and keep a clearly labelled way back to the library. These patterns also give students with limited digital experience fewer conventions to learn. [W3C WAI on older users](https://www.w3.org/WAI/older-users/), [W3C cognitive accessibility guidance](https://www.w3.org/TR/coga-usable/design_guide.html)
- **Give learners one obvious way to begin.** In over 200 think-aloud interviews, the PhET team found that students used familiar controls with immediate feedback, while playback icons often went undiscovered. In one simulation, a simpler startup state and a short cue encouraged students to start exploring. Show a usable example on arrival, start animated scenes paused, and give playback controls visible labels such as “Play”, “Pause” and “Restart”. Use one short suggestion near the relevant control and put detailed explanations where learners can open them when needed. This applies PhET’s student findings to the library. Check the design with each intended audience. [Adams et al., PhET interface-design study](https://phet.colorado.edu/publications/PhET_Interviews_II.pdf), [Podolefsky et al., PhET implicit scaffolding study](https://arxiv.org/abs/1306.6544)
- **Support keyboard, touch and precise input.** PhET interviewees often explored with sliders and switched to numeric fields for exact values. Keep the library’s slider and value field in sync, label each with its parameter and units, and explain invalid inputs next to the field. For a draggable object, provide keyboard operation and an equivalent click or tap interaction, such as step buttons. Keep keyboard focus visible and clear of overlays. Aim for at least 44 × 44 CSS pixels on primary controls, which is the WCAG enhanced target size. The AA minimum is generally 24 × 24 CSS pixels, with specified exceptions. [PhET interface-design study](https://phet.colorado.edu/publications/PhET_Interviews_II.pdf), [WCAG 2.2 keyboard access](https://www.w3.org/TR/WCAG22/#keyboard), [focus visibility and obstruction](https://www.w3.org/TR/WCAG22/#focus-visible), [pointer input criteria](https://www.w3.org/TR/WCAG22/#input-modalities)
- **Make text, controls and diagrams readable at larger sizes.** Check for at least 4.5:1 contrast for ordinary text and 3:1 for relevant control boundaries, states and essential graphical elements under WCAG AA. Add labels or line styles to graph series that rely on colour. Check 200% text resizing and reflow at 320 CSS pixels for the surrounding page and controls. Essential two-dimensional diagrams can retain their layout. [WCAG 2.2 distinguishability criteria](https://www.w3.org/TR/WCAG22/#distinguishable)
- **Expose the science outside the canvas.** In a PhET prototype, researchers explored descriptions that convey the scene and explain changes in response to user actions. Keep the current state, key values and units in accessible HTML. For example, show the horizontal and vertical velocity components as labelled values at the current projectile time. Summarise meaningful events, such as reaching the ground, and keep continuous frame updates quiet for screen readers. [Smith, Lewis and Moore, PhET description strategies](https://openresearch.ocadu.ca/id/eprint/1576/), [WCAG 2.2 non-text content](https://www.w3.org/TR/WCAG22/#non-text-content), [status messages](https://www.w3.org/TR/WCAG22/#status-messages)

## Moderated usability check

Run a 15–20 minute think-aloud session with each of 4–6 people, including older adults and A-level students who report low confidence with technology. Invite participants to use their usual device, zoom and assistive technology. Include a keyboard-only and a small-screen route across sessions. Treat the results as formative observations and check WCAG 2.2 AA independently. [W3C WAI on involving users in evaluation](https://www.w3.org/WAI/test-evaluate/involving-users/)

1. Start at the library. Ask the participant to find the AS Physics simulation for how a ball travels after launch. Observe how they choose the course, topic and simulation.
2. Ask them to run the example, stop it in mid-flight and replay it from the start. Record which controls they try first and whether they can tell if the example is running or paused.
3. Ask them to set the launch angle to exactly 45°, compare the trajectory with the starting example and explain how they could tell it changed. Observe whether they can enter an exact value and find a graph, diagram or text readout that explains the change.
4. Ask them to make a label on the picture easier to read, look at an area that moved outside the view and return to the whole picture. Record whether they discover zoom, the direction buttons and Reset view independently.
5. Ask them to restore the launch angle to its original value and return to the library. Observe whether they can distinguish restarting the motion, resetting the view and changing an input.

Give the task wording first and let the participant choose the controls. If they get stuck, ask what they expected before offering a hint. Record who completed each task independently, who needed a hint, where focus or labels caused friction, and whether each participant could recover from an unintended change. Fix any barrier that blocks a core task and rerun that task. This is a proposed check. No participants were tested for this note.
